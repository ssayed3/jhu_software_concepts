# JHU Software Concepts

This repository contains coursework for the Johns Hopkins University
Modern Software Concepts in Python course.

# Module 2 - Web Scraping and Data Cleaning

Module 2 collects graduate admissions data from GradCafe, cleans the
collected data, and uses a local language model to standardize university
and program names.

## Dataset

The original Module 2 dataset contains approximately 30,000 GradCafe
applicant records.

The main data files are:

- `applicant_data.json` - applicant records collected from GradCafe
- `llm_extend_applicant_data.json` - applicant records extended with
  standardized university and program names generated by the local LLM

The raw scraped data contains information such as:

- university
- program
- degree
- date added
- admission decision
- term
- citizenship
- GPA
- GRE scores
- comments
- applicant URL

## Web Scraping

The scraper uses BeautifulSoup to parse GradCafe applicant records.

Because GradCafe content is dynamically loaded, the scraper controls
Google Chrome using AppleScript and JavaScript to capture the rendered
HTML.

The scraper:

1. Opens GradCafe survey pages in Chrome.
2. Waits for applicant data to load.
3. Captures the rendered HTML.
4. Parses applicant records with BeautifulSoup.
5. Checks applicant URLs to prevent duplicate records.
6. Saves newly collected records to `applicant_data.json`.
7. Saves scraping progress so collection can resume from the next page.
8. Stops after collecting the configured number of additional records
   for the current run.

The scraper also checks for browser verification or blocking pages and
stops safely if one is detected.

## Data Cleaning

The collected applicant data is cleaned before analysis.

Missing values are preserved when appropriate rather than causing the
program to fail.

The cleaning process also standardizes values used later in the
database analysis.

## LLM Standardization

A local language model is used to generate standardized versions of:

- university names
- program names

These values are stored in:

- `llm-generated-university`
- `llm-generated-program`

The extended records are stored in:

`llm_extend_applicant_data.json`

These standardized fields allow the original downloaded fields to be
compared with LLM-generated versions during database analysis.

# Module 3 - Database Queries, SQLAlchemy, and Dynamic Webpages

Module 3 loads the cleaned GradCafe applicant data into PostgreSQL and
analyzes the data using both raw SQL and SQLAlchemy.

It also provides a Flask webpage that dynamically displays the analysis
results and allows newly available GradCafe records to be pulled into
the database.

## PostgreSQL Database

The project contains an `applicants` table that stores applicant
information including:

- applicant ID
- university/program information
- comments
- date added
- applicant URL
- admission status
- intended term
- nationality classification
- GPA
- GRE Quantitative
- GRE Verbal
- GRE Analytical Writing
- degree
- LLM-generated program
- LLM-generated university

Applicant URLs are unique so duplicate applicant records are not
unnecessarily inserted when data is loaded more than once.

Database credentials are not stored directly in the repository.

## Raw SQL Analysis

The Module 3 analysis uses raw SQL through psycopg to answer the required
graduate admissions questions.

The current implementation is located in:

`src/query_data.py`

## SQLAlchemy ORM

The SQLAlchemy `Applicant` model is located in:

`src/models.py`

The ORM analysis is located in:

`src/orm_queries.py`

This provides a Python-based ORM alternative to handwritten SQL queries.

## Dynamic Flask Webpage

The Flask application is located in:

`src/app.py`

The webpage dynamically retrieves PostgreSQL analysis results.

The webpage template is located in:

`src/templates/index.html`

The CSS stylesheet is located in:

`src/static/style.css`

## Pull Data

The webpage includes a **Pull Data** button.

Pull Data runs the GradCafe scraper and loads newly collected usable
records into PostgreSQL.

Applicant URLs are unique, which prevents overlapping records from being
inserted repeatedly.

A lock prevents a second scraping process from starting while another
one is already active.

## Update Analysis

The webpage also includes an **Update Analysis** button.

Update Analysis does not run the scraper.

Instead, it re-queries the current PostgreSQL database and displays the
most up-to-date analysis results.

# Running Module 4

Module 4 uses PostgreSQL, psycopg, SQLAlchemy, Flask, BeautifulSoup,
pytest, pytest-cov, and Sphinx.

## 1. Create a Virtual Environment

From the `module_4` directory:

```bash
python -m venv venv
source venv/bin/activate
```

## 2. Install Requirements

Install the required Python packages:

```bash
pip install -r requirements.txt
```

## 3. Configure PostgreSQL

PostgreSQL must be installed and running for database-dependent
functionality and integration tests.

The database connection can be supplied using the `DATABASE_URL`
environment variable.

For example:

```bash
export DATABASE_URL="postgresql://username@/module4_test_db"
```

The PostgreSQL user can also be supplied through:

```text
DB_USER
```

When `DATABASE_URL` is not supplied, the application uses its configured
local default database connection.

## 4. Run the Flask Application

From the `module_4` directory:

```bash
python -m src.app
```

Open the local Flask address displayed in the Terminal.

The analysis page is available at:

```text
/analysis
```

The webpage displays the graduate admissions analysis and provides
**Pull Data** and **Update Analysis** controls.

## 5. Pull New Data

Click **Pull Data** on the Flask webpage.

The application runs the scraper and loads newly collected applicant
records into PostgreSQL.

Applicant URLs are unique, so overlapping records are not inserted
repeatedly.

If a pull is already running, another pull request receives an HTTP
409 busy response.

## 6. Update the Analysis

Click **Update Analysis** to re-query the PostgreSQL database and
refresh the analysis.

Update Analysis does not start another scraping operation.

If the application is busy with a pull operation, the update request
receives an HTTP 409 busy response.

## 7. Run the Automated Tests

Run the complete test suite with:

```bash
python -m pytest
```

The expected completed local result is:

```text
92 passed
100% coverage
```

A specific marker can also be run separately.

For example:

```bash
python -m pytest -m web
```

or:

```bash
python -m pytest -m db
```

To run all required marker categories explicitly:

```bash
python -m pytest -m "web or buttons or analysis or db or integration"
```

# Test Design

The automated tests are designed to be deterministic.

They do not depend on live GradCafe internet access.

Fake or mocked behavior is used where appropriate for:

- scraper results
- browser interaction
- external operations
- local LLM behavior

The tests avoid arbitrary sleep calls and manual UI interaction.

The application factory supports dependency injection so tests can
provide fake scraper, loader, and analysis functions.

# Database Idempotency

Applicant URLs are unique in PostgreSQL.

This allows repeated or overlapping data pulls to remain consistent.

The integration tests verify a workflow in which:

1. The first pull provides applicant records 1 and 2.
2. The second pull provides records 2 and 3.
3. Record 2 overlaps between both pulls.
4. PostgreSQL prevents the duplicate URL from being inserted twice.
5. The final database contains three unique records rather than four.

## SQL Injection Defense

Database queries that use external or variable values use parameterized
queries rather than inserting values directly into SQL strings.

The project avoids constructing SQL queries using f-strings, string
concatenation, or `.format()` with user-controlled values.

`psycopg.sql.SQL` is used for safe SQL statement construction where
appropriate, while values are supplied separately using `%s` parameters.

Dynamic SQL identifiers can be safely represented using
`psycopg.sql.Identifier` rather than directly concatenating table or column
names into SQL statements.

A SQL injection test also verifies that malicious-looking input such as:

```text
' OR 1=1 --
```

is passed to PostgreSQL as data rather than becoming part of the SQL
statement.

## Query Result Limits

Result-returning database queries include inherent limits.

Queries that return a single aggregate or record use `LIMIT 1` where
applicable. Queries that may return multiple records are bounded rather than
being allowed to return an unlimited result set.

For queries accepting a variable result limit, the project uses a
limit-clamping function that restricts the requested limit to the safe range
of 1 through 100.

This provides an additional safeguard against unexpectedly large database
responses.

## Least-Privilege Database User

Normal application database access uses the restricted PostgreSQL role:

```text
module5_app
```

The role follows the principle of least privilege.

The verified permissions are:

- `SELECT` on the `applicants` table: allowed
- `INSERT` on the `applicants` table: allowed
- `UPDATE` on the `applicants` table: denied
- `DELETE` on the `applicants` table: denied
- sequence usage for `applicants_p_id_seq`: allowed
- creation of schema objects in `public`: denied
- PostgreSQL superuser privileges: denied
- role creation privileges: denied
- database creation privileges: denied

The `applicants` table is not owned by `module5_app`, so the normal
application role is separated from administrative table ownership.

Administrative schema creation and other privileged database operations
remain outside the normal application role.
